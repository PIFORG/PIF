# Financial parity (virtual trading, portfolios, MarketQuest)

**Status: the shared financial core (`apps/api/src/finance/`) is ported to Java and verified against the TypeScript implementation. No financial endpoint or screen is migrated, and Spring processes no financial command.** Exposing trading endpoints remains blocked until ownership checks, transaction handling and event sequencing are ported and validated, as the phase instructions require.

## Money representation in the current system

- `apps/api/src/finance/money.ts`: an **Amount** is an integer number of thousandths of the currency unit (millimes for TND; `AMOUNT_SCALE = 1000`), held in a JavaScript `number` (an IEEE-754 double).
- Balances, cost basis and P&L are integer-valued. Floating point is used for ratios (returns, weights, risk) that are never written back into balances.
- Storage: amount columns are PostgreSQL `BIGINT` with a `…Millimes` suffix.
- Rounding: `divRound` rounds half away from zero on the double quotient. Commission is `max(minimum, notional × bps / 10 000)` rounded that way, and a zero notional pays nothing.

## The Java port

Package `com.pif.api.finance` in `apps/api-spring` mirrors the 9 TypeScript source files (`money`, `execution`, `orders`, `pretrade`, `ledger`, `valuation`, `performance`, `risk`, `index`). It has 17 Java files, because records and enums such as `Holding`, `Execution`, `Booking`, `Quote`, `OrderSide` and `OrderType` live in their own files. `JsSemantics` reproduces the JavaScript behaviour the TypeScript code relies on: `Math.round` (ties toward +∞), `Number.isInteger`, and the key order of plain objects (array-index keys first, then insertion order).

Convention chosen: **amounts are kept as integer-valued `double`s, and every computation performs the same IEEE-754 operations in the same order as the TypeScript code.** A `long` or `BigDecimal` implementation would round differently from production on some inputs; see the observations below. Results are therefore compared bit for bit, sign of zero included, with no tolerance.

No HTTP endpoint uses the package yet.

### Every mismatch found, classified

**Java implementation defects: none remaining.** All 3,013 golden cases pass without tolerance, except the 2 that the approved VaR correction below reclassifies as invalid data.

| Case | Classification | Effect | Java behaviour |
| --- | --- | --- | --- |
| **Stress-line order** (`stressImpact`) for symbols containing spaces or punctuation | **Intentional convention difference** | TypeScript sorts with `localeCompare` (ICU, server locale `fr-FR`); Java uses the JDK root-locale collator. They agree on letters, digits, case and accents. Only the order of lines for symbols with spaces or punctuation differs; every line and the total are identical | Kept. The instrument symbols (`CTB`, `MDX`, `OLV`, `SFX`, `TEK`, `ATL`, `GOV` in `fictional-universe.ts`) are uppercase letters, so production output is unaffected |
| **Symbols named like `Object.prototype` members** (`__proto__`, `constructor`, …) | **Pre-existing TypeScript defect, corrected in Java (approved, phase 3)** | TypeScript keeps positions in a plain object, so the buy is charged but the holding is lost (`__proto__` even pollutes every object) | Java books them like any other symbol |
| **Historical VaR with a non-finite value (`NaN`, `±Infinity`) in the sample** | **Pre-existing TypeScript defect, corrected in Java (approved, phase 3)** | With `NaN` the result depends on V8's sort internals; with `±Infinity` TypeScript returns a VaR of 0 or a finite number next to an infinite ES | Java refuses the sample (`InvalidSampleException`) |
| **`maxWeight` with about 150,000 holdings or more** | **Pre-existing TypeScript defect, corrected in Java (approved, phase 3)** | `Math.max(...weights)` overflows the call stack | Java has no holding-count limit |

### Approved corrections (phase 3)

The three defects above were approved as intentional corrections on the condition that each is documented, covered by independent fixtures and leaves ordinary valid cases unchanged. The TypeScript code was not modified.

| Correction | Old behaviour and why it is wrong | Behaviour now | Policy |
| --- | --- | --- | --- |
| Prototype-like symbols | A position keyed `__proto__` or `constructor` is lost after the cash is charged, so cash, cost basis and holdings disagree | Every symbol is an ordinary map key (`LinkedHashMap`), whatever its spelling | Symbols are opaque strings; no symbol is reserved |
| VaR and ES with non-finite observations | A `NaN` makes the sort order engine-dependent; an infinite loss produced "VaR 0 / ES ∞" or a finite VaR, which reads as a valid (even zero-risk) result | `Risk.historicalVaR` throws `InvalidSampleException` when any observation is `NaN` or infinite and the sample is long enough to compute (30 or more). Below 30 observations it still returns "unavailable" (`null`), as before | **Missing-data policy:** a sample with an invalid observation is invalid as a whole. Callers must report the metric as unavailable with a reason; they must never substitute zero or drop the bad points silently |
| `maxWeight` for very large books | Above about 150,000 holdings the call stack overflows and the request fails | A single pass over the holdings | **Denominator:** portfolio equity (cash plus holdings at their valuation prices). **Rounding:** one IEEE-754 division per holding (correctly rounded) and no further rounding; the result is the largest ratio. **Degenerate cases:** 0 when there are no holdings or equity ≤ 0. No holding-count limit |

**Independent regression fixtures.** `src/test/resources/fixtures/finance-corrections.json` holds hand-derived expectations that do not come from the TypeScript output. `FinanceCorrectionsTest` (6 tests) checks them with `BigDecimal` (`DECIMAL128`) arithmetic:

- a buy and a partial sale on each of 9 `Object.prototype` names (`__proto__`, `constructor`, `toString`, `hasOwnProperty`, …), with expected cash, cost basis, realized P&L, fees and spread cost;
- VaR and ES of a 30-value sample (VaR 29, ES 29.5), the `NaN`, `+Infinity` and `-Infinity` variants (refused), and a 29-value sample containing `NaN` (unavailable);
- `maxWeight` over 200,001 holdings, an ordinary three-holding case and the degenerate cases.

**Golden-master impact.** Of the 82 `historicalVaR` golden cases, exactly 2 (cases 17 and 18: one `-Infinity` and one `+Infinity` observation) are now expected to be refused instead of matching TypeScript. `FinanceGoldenMasterTest.exactlyTwoGoldenValueAtRiskCasesAreReclassifiedAsInvalidData` pins that count, so any further divergence fails the build. The other 3,011 golden cases still match TypeScript bit for bit. No persisted data changes: these functions only compute analytics that are never written back into balances.

### Floating-point behaviour reproduced deliberately

These are not mismatches: Java reproduces them exactly. They are recorded because a "corrected" implementation would silently change production results.

| Observation | Example | Cases in the fixture |
| --- | --- | --- |
| `toAmount` differs from exact decimal half-up rounding when the decimal value is not representable as a double | `toAmount(65742.2805)` gives 65742280; exact half-up would give 65742281 | 10 |
| `limitWithinBand` rejects some limit prices lying exactly on the band edge, because of floating-point error in the band computation | limit 3, mid 10, band 70 % | 12 |

Changing either convention (for example moving to `BigDecimal`) would be an intentional correction and needs explicit approval.
